# Информационная безопасность

## 1. Что важно понимать заранее

Соответствие требованиям ФСТЭК России — свойство **информационной системы в целом** (программа + сервер + сеть + организационные меры + аттестация), а не только программы. ПК «Кафедра» реализует встроенные механизмы защиты и снимает с оператора большую часть технической работы, но не заменяет:

- определение класса защищённости / уровня защищённости ПДн и модели угроз;
- сертифицированные средства защиты там, где они обязательны (ОС, межсетевой экран, антивирус, СКЗИ);
- организационно-распорядительные документы и аттестацию.

Применимые акты (сверяйте с актуальными редакциями): 152-ФЗ и ПП РФ № 1119 (персональные данные учащихся и работников), приказ ФСТЭК России № 21 (меры защиты ПДн); для государственных учреждений — приказ ФСТЭК России № 117 от 11.04.2025, действующий с 1 марта 2026 г. взамен приказа № 17; ГОСТ Р 56939-2024 (безопасная разработка).

ПК «Кафедра» **не является сертифицированным средством защиты информации**. Если сертификация потребуется, она проводится отдельно в системе сертификации ФСТЭК России.

## 2. Хранение паролей без аппаратного хранилища

Задача: чтобы утечка базы данных не давала возможности подобрать пароли, не используя HSM или токены.

Решение — разделение секрета между базой и отдельным файлом ключа:

1. При инициализации создаётся случайный **мастер-ключ** 256 бит: файл `master.key`, права `0600`, владелец — служебная учётная запись. Программа отказывается запускаться, если файл доступен другим пользователям.
2. Из мастер-ключа по HKDF-SHA256 выводятся независимые ключи: «перец» для паролей и ключ шифрования секретов второго фактора.
3. Пароль хранится как `PBKDF2-HMAC-SHA256( HMAC-SHA256(перец, пароль), соль 128 бит, 600 000 итераций )`. Соль индивидуальна, число итераций записано в хеше и повышается без сброса паролей (перехеширование при входе).
4. Мастер-ключ **не попадает** в автоматические резервные копии и копии, выгружаемые через браузер.

Итог: похититель базы или резервной копии без файла ключа не может проверить ни одного варианта пароля; похититель одного лишь ключа не получает ничего. Сравнение — за постоянное время; для несуществующих логинов выполняется такая же по длительности проверка.

Дополнительно: история паролей, срок действия, запрет логина в пароле и распространённых паролей, генерация временных паролей криптографическим генератором, обязательная смена при первом входе, показ временного пароля один раз.

> Об алгоритмах. Использованы алгоритмы стандартной библиотеки Go (SHA-256, AES-256-GCM, TLS 1.2/1.3). Они не являются российскими криптографическими стандартами. Если для вашей системы обязательна защита каналов сертифицированными СКЗИ (ГОСТ), разместите перед сервером сертифицированный TLS-шлюз (раздел 8 руководства администратора) — прикладная часть при этом не меняется.

## 3. Реализованные механизмы и меры (по группам приказа ФСТЭК № 21)

| Группа мер | Реализация в продукте | Остаётся оператору |
|---|---|---|
| **ИАФ** Идентификация и аутентификация | уникальные логины; парольная политика (длина, классы символов, история, срок); второй фактор TOTP (RFC 6238) с защитой от повторного использования кода, обязателен для администраторов по умолчанию, настраивается для преподавателей и всех; единое сообщение об ошибке входа; ограничение частоты попыток по адресу | регламент выдачи учётных записей |
| **УПД** Управление доступом | три роли; проверка прав на сервере для каждого запроса и каждого объекта (курс, файл, попытка, работа, портфолио); блокировка после N неудачных входов; завершение сеанса по бездействию и по предельной длительности; ограничение числа одновременных сеансов; немедленное прекращение сеансов при отключении, смене роли или пароля; принудительное завершение сеансов администратором | матрица доступа, пересмотр прав |

Запись: время, пользователь, адрес, событие, объект, результат. **Цепочка хешей SHA-256** делает удаление и правку записей обнаружимыми. ## 4. Защита веб-приложения

| Угроза | Мера |
|---|---|
| Межсайтовый скриптинг (XSS) | автоэкранирование шаблонов; собственный преобразователь разметки экранирует весь ввод и пропускает ссылки только `http(s)`, `mailto`, локальные; строгая Content-Security-Policy без встроенных сценариев и внешних источников |

| Утечка через кеш | `Cache-Control: no-store` для страниц |

## 5. Персональные данные (152-ФЗ)

- Минимальный состав: ФИО, логин, необязательная почта, группа, сведения об успеваемости и действиях.
- Согласие фиксируется при первом входе (дата хранится в учётной записи и в журнале). Текст согласия в шаблоне `password.html` согласуйте с вашим юристом: наличие отметки в системе не заменяет оформления согласия по правилам организации.
- Удаление учётной записи удаляет связанные персональные данные (попытки, работы, оценки, портфолио, уведомления).
- Рейтинг по умолчанию не раскрывает ФИО других учащихся.
- Данные хранятся только на сервере организации; обращений к внешним ресурсам нет.

## 6. Рекомендации по развёртыванию

1. ОС из числа сертифицированных (Astra Linux SE, РЕД ОС, Альт СП), обновления, шифрование диска с данными.
2. Сертификат УЦ; порт 443 — единственный открытый извне; SSH только из сети управления.
3. Копия `master.key` — отдельно от резервных копий.
4. Включите второй фактор для преподавателей («Настройки»).
5. Передавайте строки `AUDIT` из journald в систему мониторинга; раз в неделю запускайте `kafedra audit-verify`.
6. Синхронизация времени (NTP) — от неё зависят журнал и одноразовые коды.

## 7. Известные ограничения

- Журнал событий защищён от незаметной правки, но не от уничтожения целиком пользователем с правами root; для этого нужна внешняя система сбора журналов.
- Данные на диске не шифруются программой (кроме секретов второго фактора); используйте шифрование тома.
- Независимый аудит безопасности и тестирование на проникновение не проводились — рекомендуются до ввода в эксплуатацию.
- QR-код для подключения аутентификатора не формируется: ключ вводится вручную.
